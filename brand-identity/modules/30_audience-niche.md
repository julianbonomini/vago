## Synthesis

Possible early users named by the founder: solo developers, vibe coders, and developers building proofs of concept. Solo developers and vibe coders seem most likely to try an unfinished Alpha. No single first audience has been chosen yet.

The founder does not want to limit Vago by the type of software being built. They are using Vago to build Vago. Audience discovery should focus on the developer's working situation and need to delegate execution, rather than a Project category.

The likely early user has a defined feature, bug, or idea but still spends attention supervising agents, correcting them, and handling small issues. The founder wants a handoff closer to assigning well-defined work to a development team.

Observed example from Vago's own development: the founder defined what a good PR description should be, submitted a Goal and its Tickets, and returned to finished work. This is one successful handoff, not evidence of general reliability.

Without Vago, the founder would prompt an agent, correct it during the work, and rebrief a new session when the context grew too large. Repeated supervision and session handoffs are the specific work the early user wants to stop doing.

Vago's intended user knows the Workflow they want. Vago includes the founder's own Workflows as starting points, but does not help a user discover the right Workflow for their Project. The earlier "anyone" answer meant setup is not restricted to a particular kind of developer; it did not mean Vago teaches process design.

The founder sees a poor fit in users who use AI without much thought about how to work with agents. This is a working audience distinction, not a tested ability criterion.

A concrete good-fit user already uses agent skills to guide a loose Workflow and deliberately improves how agents work for them. The founder cited Matt Pocock's skills and Superpowers as examples of that practice.

Candidate first-audience formulations, for discussion:

1. Solo developers who have a repeatable way of working with agents and want to stop managing each session.
2. Developers who already use agent skills and want their own Workflow to carry work forward while they are away.
3. People building with agents who can define both the Goal and the Workflow, then want to hand off execution.

Open questions:

- Which of these users can complete the Alpha setup and first Goal without the founder's help?
- How many early users already have a Workflow they can describe, rather than only a set of prompts or skills?
- Which jobs create enough repeated agent supervision to motivate setup?

Tensions to revisit:

- "Vibe coder" may include people who do not yet have a Workflow they trust. The founder expects the user to supply that judgment.
- The audience wants to stop babysitting agents. Alpha can still stop on a failed Step and need human intervention.
