# Architecture

Vago Alpha's modules, what each one owns and hides, and the rules between them. The behaviour of each module is in the spec (`.scratch/vago-alpha/spec.md`, Implementation Decisions); this file covers boundaries only. A ticket that changes a boundary updates this file in the same PR.

## Layout

```
src/cli.ts                  src/goal-runner.ts      src/progress.ts
src/workflow.ts             src/step-runner.ts      src/init.ts
src/tickets/tickets.ts      src/worktree.ts
src/tickets/header.ts       src/tickets/ticket-folder.ts    src/tickets/goal-lock.ts
src/harness/registry.ts     src/harness/claude-code.ts
src/tui/tui.tsx             src/tui/project-view.tsx        src/tui/goal-rows.ts
src/tui/goal-preview.tsx    src/tui/ticket-bar.tsx          src/tui/time-and-money.ts
src/tui/screen-keys.tsx     src/tui/theme.ts                src/tui/text-fit.ts
src/tui/goal-view.tsx       src/tui/goal-tickets.ts         src/tui/run-line.tsx
src/tui/run-activity.tsx    src/tui/goal-start.ts
                                                            the TUI, drawn with OpenTUI and Solid
src/starter-imports.d.ts    types for init.ts's text imports of the starter
build.ts                    the Bun.build script `bun run reinstall` runs
bunfig.toml                 Solid's preload for `bun test` and `bun src/cli.ts`
starter/                    the starter Workflows and skills embedded in the binary
.vago/                      Vago's own Workflow: the starter plus Vago's docs as includes
.vago-goals/                Goals and Tickets, untracked and kept apart from the .vago/ config
test/                       CLI tests, the fake `claude`, recorded fixtures, a fixed Workflow
```

One file per module. A module becomes a folder only when it outgrows about 400 lines, and the folder exposes one entry file. Other modules import only that entry file; the folder's other files are private to it. `tickets/` is such a folder: its entry is `tickets/tickets.ts`, `header.ts` holds the `+++` header format and atomic rewrites, `ticket-folder.ts` reads a Goal's `tickets/` folder and checks numbers and blockers, and `goal-lock.ts` holds `running.lock`. `tui/` is another, whose entry is `tui/tui.tsx`: `project-view.tsx` lays out the Project view, reads its Goals again every second, keeps the selection on its Goal and moves it by key and click, and opens the selected Goal in the Goal view, and the Goal before or after it on `[` and `]`, `goal-preview.tsx` the selected Goal's preview under its table, `goal-rows.ts` turns Goals into the table's rows and what the preview and the Goal view show of each, a Goal it can't read becoming a broken row with the error, and counts a Goal's Tickets and tokens, reading the Steps of each Workflow a Goal's Tickets go through and when each open Run last wrote its log, `goal-view.tsx` lays out the Goal view under the Project view's header: its Goal box, its Tickets, the selected Ticket's text and Runs, the selected Run with a shell Run's log or an agent Run's activity, its log read again every second for what it added, which pane has the focus and which has the whole screen, its footer of keys and its help screen, and the keys and clicks that move the selections and the focus and follow an open Run, `run-activity.tsx` draws an agent Run's activity: the session's divider, the prose blocks with tool calls indented under them and failures further in, the end block, and the `working` line of a live Run whose agent has the turn, `goal-start.ts` starts a ready Goal in a `vago run` of its own, cut loose from the TUI and its terminal, and refuses any other, `run-line.tsx` draws one Run on a line for the preview and the Runs pane, `goal-tickets.ts` turns a Goal's Tickets into what the Goal view and the preview show of each: its mark, its state word, its Workflow's Steps marked from its latest pass, its Runs and their totals, and its text; it is the one module that says whether an open Run is live or lost and times a lost one to its log's last write, and the one that spells the Step a running Ticket is on, `ticket-bar.tsx` draws a Goal's progress bar, sharing its cells between Ticket statuses, `time-and-money.ts` spells durations, times of day, dollars and token counts, `screen-keys.tsx` draws a screen's footer of keys and its help screen, `pane-grid.ts` draws every pane's border as one grid of lines, joined where two panes share an edge, with their titles and the focused pane's outline, `theme.ts` holds the colour tokens, symbols and borders, the look of each mark it is handed and of a focused pane, and is the one file of `tui/` that reads `NO_COLOR` and `VAGO_ASCII`, and `text-fit.ts` cuts or wraps text to a column by display width and joins hard-wrapped Markdown into paragraphs. Tests may import `tui/project-view.tsx`, the view seam, directly.

## Modules

| Module | Owns | Hides from everyone else |
|---|---|---|
| `cli.ts` | Commands, argument parsing, each command's help and usage text, exit codes, printing errors, reading a `--body-file` from a path or stdin | `process.argv`, `process.exit`, which exit code means what, the `-` for stdin convention |
| `workflow.ts` | Loading and checking `.vago/workflows/<name>.toml`, the Workflow a Goal names, and its prompt files, refusing a name that isn't there with a list of the names that are, returning the frozen Workflow, building an agent Step's prompt from it, and the ids of a Workflow's Steps read from its TOML alone, for the TUI | Which Workflows exist in `.vago/workflows/`, the TOML schema, defaults (`idle_timeout`, `on_fail`, `when`), path resolution, include merging, substitution syntax (`{{ticket}}`, `{{goal}}`, `{{goal_name}}`, `{{steps.<id>.output}}`) |
| `tickets/` | Goal and Ticket files: creating them, a Goal or Ticket with a given body or a title to fill in, the `goal.md` header, which names only the Goal's `workflow` and which the human may edit by hand between runs, the Workflow each Ticket goes through, its own or the Goal's, format checks, readiness, whether a Ticket is its Goal's last, status, `[[runs]]`, log paths, reading a growing log a piece at a time and when a log was last written; how a Ticket number is spelled, which Ticket file names, log names, the TUI and the reset hint all share; each Goal's and Ticket's title and the text after it, each Ticket's blockers; the mark that a `vago run` has a Goal, held while it runs, and whether another live `vago run` has it; the Goals of a Project | The `+++` header format, the `.vago-goals/<goal>/` layout, log naming, atomic writes; the lock file, and how a dead run's lock is taken over |
| `goal-runner.ts` | Creating a Goal or a Ticket with the Workflow it names, refused when `vago run` would refuse it; the main loop: lost and stuck handling, picking Tickets, running Steps in order and skipping a `last-ticket` Step on any other Ticket, marking `done`; opening the Goal's worktree, where its Steps run, once it has a ready Ticket; closing the Goal's worktree once every Ticket is done; running the Goal only while no other `vago run` has it | The order of a Goal's lifecycle and where its Steps run |
| `worktree.ts` | A Goal's worktree: creating it on `vago/<goal>` from the default branch with the main checkout's untracked and ignored files, recreating it from an existing `vago/<goal>` after the human deletes it, reusing it, keeping `.vago/` current, tracked or not, and out of the worktree's git, removing it, branches kept, once the Goal is done and nothing in it would be lost, and the Project root from inside it | The `VAGO_HOME` layout, the branch name, the default-branch rule, git commands, what gets copied, how `.vago/` is kept out of git, what counts as a change or as pushed |
| `step-runner.ts` | Running one Step on a Ticket as one Run, in the Goal's worktree it's given: its `[[runs]]` entry, its Step lines, its prompt, its child process and its log | Spawning, process groups, signals, the idle timer, writing the log, reading the Harness stream |
| `progress.ts` | Everything printed during a run: the Goal's worktree, a line naming each Ticket as it starts with its Step lines under it, the `stuck` message, the Goal summary table, what became of the Goal's worktree. Also the Markdown Goal report `vago goal report` prints | Line formats, column widths, colour and when stdout gets it, durations, cost formatting |
| `init.ts` | `vago init`: copying the starter, every Workflow included, into `.vago/` and its `vago-` skills into `.claude/skills/`, refusing when a file it would write already exists, asking whether the Workflow will be committed, `.git/info/exclude`. `vago update`: rewriting the starter files that differ, keeping the commit answer the exclude records | The starter's file list and how it's embedded, where each file goes in the Project, exclude lines |
| `tui/` | `vago` with no command on a terminal: holding the terminal while the TUI is open and restoring it on every way out, holding stderr and `console`, the quit keys, and the Project view, read again every second, with its selection, which follows its Goal when the rows reorder and moves by key and click, its rows scrolled by the wheel, its footer of keys and its help screen; the Goals table: a Goal's standing (running, lost, stuck, broken, ready, done), its "now" phrase, run time (its Runs' time added up) and cost, the order of the rows, and the header line's totals, which stays at the top of every screen; the selected Goal's preview: its latest Runs and its description with `goal.md`'s paragraphs joined; the Goal view, opened by Enter and closed by Esc: the Goal box with the Goal's place in the list, progress bar, state, run time, tokens, cost, Workflow and title, its Tickets with their state words, and the selected Ticket's title, blockers, Steps marked done, current, failed, lost or pending from its latest pass, its Runs' totals and its text with its paragraphs joined, its Runs listed and picked with ←→, and the selected Run with its outcome, time and cost, a shell Run's log or an agent Run's activity, its prose in blocks cut after 40 lines and its tool calls indented under it; the focus, moved by Tab and 1 to 4, which the arrows scroll or move in, the Ticket's or the Run's whole screen on `t` and `r`, the Goal before or after on `[` and `]`, a click picking a Ticket, a Run or a pane, the wheel scrolling the pane under the pointer, and the footer of keys and the help screen; starting the selected Goal on `s` in the Project view and the Goal view, a ready one only, as a `vago run` it never owns, with what came of it in the footer; an open Run followed as its log grows until scrolled up and again on `G`, marked live, or lost after its last write when no `vago run` holds the Goal, which a line in the Goal box then says; the boxes edge to edge, neighbours sharing one border line | OpenTUI, Solid, the renderer, the alternate screen, the signal and error handlers, how a started `vago run` outlives the TUI, the colour tokens and symbols, display-width fitting, column layout, the border junctions, how the activity is laid out, how often the Goals are read again |
| `harness/registry.ts` | The `Harness` type, the Run activity type every Harness's stream turns into, and the map from `harness` name to module | Which Harnesses exist |
| `harness/claude-code.ts` | Claude Code's command, stream reading and resume hint, and its stream condensed into Run activity: the session's start and end, the agent's prose, one item per run of tool calls of one verb, which tools work on files, paths in the Goal's worktree or the Project shown relative to the Project, failed results, refused calls | Claude Code's flags, `stream-json` event shapes and tool names |

## Rules

1. **Only `tickets/` touches `.vago-goals/`.** It reads and writes `goal.md` and Ticket files, and it names each Run's log path. `step-runner.ts` writes the log at the path it's given. No other module builds a path under `.vago-goals/`.
2. **Only `tickets/` writes status.** Agents never see a header: `{{ticket}}` is the title and body only, and `{{goal}}` is `goal.md` after its header (ADR 0003).
3. **Every Step runs through `step-runner.ts`,** and it's the only module that spawns a Step's process. `worktree.ts` spawns git for the Goal's worktree, and `tui/goal-start.ts` spawns `vago run` for a Goal the human starts from the TUI. A sandbox later wraps the Step point.
4. **Harness modules are pure.** They build a command, read one stream line, turn a Run's stream into Run activity that doesn't depend on the Harness, and give a resume hint. They do no I/O and import only the `Harness` type from `registry.ts`. The kernel owns spawning, the idle timer, logs, `[[runs]]` and outcomes. Adding a Harness is one module plus one registry entry.
5. **Each Workflow is frozen once per `vago run`.** `workflow.ts` reads the toml, prompts and include files at load, and returns a frozen value carrying their text. `goal-runner.ts` loads the Goal's Workflow and every one its unfinished Tickets name before the first Run, and nothing re-reads them mid-Goal. Only a Ticket added mid-Goal that names a Workflow not loaded yet has it loaded when that Ticket comes up.
6. **Building a prompt does no I/O.** `workflow.ts` turns the template and the texts it's given into the prompt.
7. **Only `progress.ts` writes stdout during a run** or for `goal report`. It never prints agent text. `cli.ts` writes errors to stderr. While the TUI is open, only `tui/tui.tsx` writes to the terminal; a `vago run` the TUI starts writes nowhere.
8. **Only `cli.ts` reads `process.argv` or calls `process.exit`.**
9. **The kernel owns the Goal's worktree and its branch `vago/<goal>`**, in `worktree.ts`, and every other git action is the Workflow's (ADR 0004). `init.ts` also appends to `.git/info/exclude`, for `init` and `update`.
10. **Imports go one way:** `cli.ts` → `goal-runner.ts` / `init.ts` → the rest, and `step-runner.ts` → `harness/registry.ts` → Harness modules. `cli.ts` also imports `tickets/tickets.ts` with `progress.ts` for `goal report`, which only reads files. `progress.ts` imports `tickets/tickets.ts` for its types and `ticketNumberText`, so its reset hint spells a Ticket number as file names do. `goal-runner.ts` imports `worktree.ts` to open and close a Goal's worktree, `cli.ts` imports it for `projectRoot`, and `worktree.ts` imports only `goalsFolderName` from `tickets/tickets.ts` and `vagoFolderName` from `workflow.ts`, and nothing else of Vago's. `cli.ts` imports `tui/tui.tsx` only through a dynamic `import()`, only for `vago` with no command on a terminal, and hands it the command that runs this same `vago`, and files in `tui/` import `tickets/tickets.ts`, `readWorkflowStepIds` from `workflow.ts` for the Steps a Ticket goes through, and `harness/registry.ts` for an agent Run's activity, and nothing else of Vago's. No cycles. `tickets/` and `progress.ts` are leaves: they take plain values and never import the modules that call them. A type lives with the module that owns the concept it describes, never where it happens to avoid a cycle. A Harness module's type-only import of `Harness` (rule 4) is erased at runtime and doesn't count, and neither does `progress.ts`'s type-only import of the `WorktreeClose` type from `worktree.ts`.
11. **Each module owns its types** and exports them beside its functions. There's no shared `types.ts`.
12. **Ticket writes survive a crash.** Every header rewrite writes a temp file and renames it over the Ticket, keeping the body byte for byte. A Run's `[[runs]]` entry is written before its Step starts and filled in when it ends.
13. **The kernel never imports the TUI.** No module but `cli.ts` imports `tui/tui.tsx`, and `cli.ts` only through a dynamic `import()`, so no command loads OpenTUI or needs Solid's transform, and every command test runs as if the TUI weren't there (ADR 0005).
