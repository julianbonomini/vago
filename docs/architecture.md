# Architecture

Vago Alpha's modules, what each one owns and hides, and the rules between them. The behaviour of each module is in the spec (`.scratch/vago-alpha/spec.md`, Implementation Decisions); this file covers boundaries only. A ticket that changes a boundary updates this file in the same PR.

## Layout

```
src/cli.ts                  src/goal-runner.ts      src/progress.ts
src/workflow.ts             src/pass-runner.ts      src/init.ts
src/step-runner.ts          src/planning-runner.ts  src/sandbox.ts
src/markdown-paragraphs.ts
src/tickets/tickets.ts      src/worktree.ts
src/tickets/header.ts       src/tickets/ticket-folder.ts    src/tickets/goal-lock.ts
src/tickets/planning-chat.ts        src/tickets/planning-proposal.ts
src/harness/registry.ts     src/harness/harness-session.ts  src/harness/claude-code.ts
src/harness/codex.ts
src/tui/tui.tsx             src/tui/project-view.tsx        src/tui/goal-rows.ts
src/tui/goal-preview.tsx    src/tui/ticket-bar.tsx          src/tui/time-and-money.ts
src/tui/screen-keys.tsx     src/tui/theme.ts                src/tui/text-fit.ts
src/tui/goal-view.tsx       src/tui/goal-tickets.ts         src/tui/run-line.tsx
src/tui/run-activity.tsx    src/tui/detached-vago.ts        src/tui/planning-view.tsx
src/tui/planning-question.tsx       src/tui/planning-preview.tsx    src/tui/live-run-log.ts
                                                            the TUI, drawn with OpenTUI and Solid
src/starter-imports.d.ts    types for init.ts's text imports of the starter
build.ts                    the Bun.build script `bun run reinstall` runs
bunfig.toml                 Solid's preload for `bun test` and `bun src/cli.ts`

```

One file per module. A module becomes a folder only when it outgrows about 400 lines, and the folder exposes one entry file. Other modules import only that entry file; the folder's other files are private to it. `tickets/` is such a folder: its entry is `tickets/tickets.ts`, `header.ts` holds the `+++` header format and atomic rewrites, `ticket-folder.ts` reads a Goal's `tickets/` folder and checks numbers and blockers, `goal-lock.ts` holds `running.lock`, `planning-chat.ts` holds a planning item's `planning/chat.toml`, and `planning-proposal.ts` holds its `planning/proposal.toml` and `planning/workflow.toml` and the schema of the proposal block an agent's answer ends with. `tui/` is another, whose entry is `tui/tui.tsx`: `project-view.tsx` lays out the Project view, reads its Goals again every second, keeps the selection on its Goal and moves it by key and click, and opens the selected Goal in the Goal view, and the Goal before or after it on `[` and `]`, `goal-preview.tsx` the selected Goal's preview under its table, `goal-rows.ts` turns Goals into the table's rows and what the preview and the Goal view show of each, a Goal it can't read becoming a broken row with the error, and counts a Goal's Tickets and tokens, reading the Steps of each Workflow a Goal's Tickets go through and when each open Run last wrote its log, `goal-view.tsx` lays out the Goal view under the Project view's header: the Goal's rows in the header area, its Tickets, the selected Ticket's text and Runs, the selected Run with a shell Run's log or an agent Run's activity, its log read again every second for what it added, which pane has the focus and which has the whole screen, its footer of keys and its help screen, and the keys and clicks that move the selections and the focus and follow an open Run, `run-activity.tsx` draws an agent Run's activity: the session's divider, the prose blocks with tool calls indented under them and failures further in, edits, background tasks and loaded Skills, a running call's clock, the end block, and the `working` line of a live Run whose agent has the turn; it says which items are edits and draws an edit's diff, `detached-vago.ts` starts a ready Goal's `vago run`, refusing any other Goal, and a planning turn's `vago plan say`, each cut loose from the TUI and its terminal, `live-run-log.ts` reads a growing Run or turn log again every second for what it added, `planning-view.tsx` lays out a planning item's chat, opened from the Goals list, with its message field and the Preview beside it, `planning-preview.tsx` draws a planning item's Proposal, whether it is ready to accept, and the picker of its Workflow, `planning-question.tsx` draws what the Project view asks before it makes, renames or discards a planning item, with the field a name is typed in and the keys that answer it, `run-line.tsx` draws one Run on a line for the Runs pane, marked when it resumed a session or fell back to a fresh one, `goal-tickets.ts` turns a Goal's Tickets, and its `before_all` and `after_all` Goal Steps listed before and after them like Tickets, into what the Goal view and the preview show of each: its mark, its state word, its Workflow's Steps marked from the latest pass that `tickets/` finds, its Runs and their totals, and its text; it is the one module that says whether an open Run is live or lost and times a lost one to its log's last write, and the one that spells the Step a running Ticket is on, with the time left while it waits to retry that Step, `ticket-bar.tsx` draws a Goal's progress bar, sharing its cells between Ticket statuses, `time-and-money.ts` spells durations, times of day, dollars and token counts, `screen-keys.tsx` draws a screen's footer of keys and its help screen, `pane-grid.ts` draws the lines between panes as one grid, joined where two panes share an edge, with a line over the panes and one under them but none down their sides, and no text on any line, `pane-title.tsx` draws a pane's title row, its title on the left, in the accent when the pane has the focus, and its numbers on the right, `theme.ts` holds the colour tokens, symbols and borders, the look of each mark it is handed and of a focused pane's title, and is the one file of `tui/` that reads `NO_COLOR` and `VAGO_ASCII`, and `text-fit.ts` cuts or wraps text to a column by display width and turns hard-wrapped Markdown into the paragraphs to wrap, joined as `markdown-paragraphs.ts` joins them. Tests may import `tui/project-view.tsx`, the view seam, directly.

## Rules

1. **Only `tickets/` touches `.vago-goals/`.** It reads and writes `goal.md` and Ticket files, and it names each Run's log path. `step-runner.ts` writes the log at the path it's given. No other module builds a path under `.vago-goals/`.
2. **Only `tickets/` writes status.** Agents never see a header: `{{ticket}}` is the title and body only, and `{{goal}}` is `goal.md` after its header (ADR 0003).
3. **Every Step and every planning turn runs its process through `step-runner.ts`,** the only module that spawns a Step's or an agent's process. It wraps a read-only session, a planning turn's, in the sandbox from `sandbox.ts`. `worktree.ts` spawns git for the Goal's worktree, and `tui/detached-vago.ts` spawns `vago run` for a Goal the human starts from the TUI and `vago plan say` for a message the human sends a planning item's agent.
4. **Harness modules are pure.** A Harness module is a `HarnessCli`: it builds a command and the command that resumes a session, reads one stream line as session events, lists its models' prices and gives a resume hint, and holds nothing another Harness would need too. `harness-session.ts` turns the events into the `HarnessSessionReport` and the Run activity, which don't depend on the Harness. Neither does I/O, and a Harness module imports only types from `harness-session.ts`. The kernel owns spawning, the idle timer, logs, `[[runs]]` and outcomes. Adding a Harness is one module plus one registry entry.
5. **Each Workflow is frozen once per `vago run`.** `workflow.ts` reads the toml, prompts and include files at load, and returns a frozen value carrying their text. `goal-runner.ts` loads the Goal's Workflow and every one its unfinished Tickets name before the first Run, and nothing re-reads them mid-Goal. Only a Ticket added mid-Goal that names a Workflow not loaded yet has it loaded when that Ticket comes up.
6. **Building a prompt does no I/O.** `workflow.ts` turns the template and the texts it's given into the prompt.
7. **Only `progress.ts` writes stdout during a run** or for `goal report`. It never prints agent text. `cli.ts` writes errors to stderr, and prints the agent's answer for `vago plan say`, which is that command's result. While the TUI is open, only `tui/tui.tsx` writes to the terminal; a `vago run` or `vago plan say` the TUI starts writes nowhere.
8. **Only `cli.ts` reads `process.argv` or calls `process.exit`.**
9. **The kernel owns the Goal's worktree and its branch `vago/<goal>`**, in `worktree.ts`, and every other git action is the Workflow's (ADR 0004). `init.ts` also appends to `.git/info/exclude`, for `init` and `update`.
10. **Imports go one way:** `cli.ts` → `goal-runner.ts` / `init.ts` → the rest, `goal-runner.ts` → `pass-runner.ts` → `step-runner.ts`, with `goal-runner.ts` never importing `step-runner.ts`, and `step-runner.ts` → `harness/registry.ts` → Harness modules and `harness/harness-session.ts`. `cli.ts` → `planning-runner.ts` → `step-runner.ts`, `tickets/tickets.ts` and `workflow.ts`, with a type-only import of `HarnessSessionReport` from `harness/registry.ts`; `step-runner.ts` → `sandbox.ts`, a leaf. `cli.ts` imports `listWorkflows` from `workflow.ts` for `plan workflow`. `cli.ts` also imports `tickets/tickets.ts` with `progress.ts`, and `readRunOutput` from `step-runner.ts`, for `goal report`, which only reads files. `progress.ts` imports `tickets/tickets.ts` for its types, `ticketNumberText`, so its reset hint spells a Ticket number as file names do, and `ticketRunResumeWords`, so the Goal report marks a resumed Run as the TUI does, `runOwnerGoal`, so a Goal Step's stuck lines name its Goal, and `markdown-paragraphs.ts` to join `goal.md`'s paragraphs. `goal-runner.ts` imports `worktree.ts` to open and close a Goal's worktree, `cli.ts` imports it for `projectRoot`, and `worktree.ts` imports only `goalsFolderName` from `tickets/tickets.ts` and `vagoFolderName` from `workflow.ts`, and nothing else of Vago's. `cli.ts` imports `tui/tui.tsx` only through a dynamic `import()`, only for `vago` with no command on a terminal, and hands it the command that runs this same `vago`, and files in `tui/` import `tickets/tickets.ts`, `readWorkflowStepNames` with its `NamedWorkflow` and `NamedStep` types and the `GoalStepGroup` type from `workflow.ts` for the Steps a Ticket or a Goal Step group goes through, `listWorkflows` from `workflow.ts` for the Workflows a Proposal may name, `harness/registry.ts` for an agent Run's activity, and `markdown-paragraphs.ts` to join a Goal's or a Ticket's paragraphs, and nothing else of Vago's. No cycles. `tickets/`, `progress.ts` and `markdown-paragraphs.ts` are leaves: they take plain values and never import the modules that call them. A type lives with the module that owns the concept it describes, never where it happens to avoid a cycle. Type-only imports of `registry.ts`'s types by `harness-session.ts` and of `harness-session.ts`'s by a Harness module (rule 4) are erased at runtime and don't count, and neither does `progress.ts`'s type-only import of the `WorktreeClose` type from `worktree.ts`.
11. **Each module owns its types** and exports them beside its functions. There's no shared `types.ts`.
12. **Ticket, `goal.md`, `chat.toml`, `proposal.toml` and `workflow.toml` writes survive a crash.** Every header rewrite writes a temp file and renames it over the Ticket or `goal.md`, keeping the body byte for byte, and `chat.toml`, `proposal.toml` and `workflow.toml` are written the same way. A Run's `[[runs]]` entry is written before its Step starts and filled in when it ends.
13. **The kernel never imports the TUI.** No module but `cli.ts` imports `tui/tui.tsx`, and `cli.ts` only through a dynamic `import()`, so no command loads OpenTUI or needs Solid's transform, and every command test runs as if the TUI weren't there (ADR 0005).
